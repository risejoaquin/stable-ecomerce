## 1. Executive Summary & Objective

In PL20-01, the real commercial schema contract was established, isolating legacy unprovenanced seed rows and binding revenue strictly to real database columns (`paid_at`, `financial_status`, `total`, `refunded_amount`).

In PL20-02, the technical evidence integrity model is established. The runtime Node process must never fabricate CI verification (e.g. claim unit tests, builds, E2E suites, or release gates passed merely because the runtime endpoint was triggered). Technical datum is strictly classified into distinct semantic classes, bound to `validated_commit_sha`, and evaluated against the active deployment.

---

## 2. Evidence Classification Hierarchy

Every technical, operational, and commercial datum is classified into one of the following canonical provenance categories:

| Classification | Definition | Examples | Mutability via Runtime Probes |
|---|---|---|---|
| `RUNTIME_OBSERVED` | Data measured directly by the currently running Node process. | `runtime_database_connectivity`, `security_baseline_enforcement`, memory RSS usage (`runtime_health`) | Measured dynamically on endpoint invocation |
| `CI_EVIDENCE` | Verification generated by automated CI/CD pipelines (GitHub Actions, test runners, scanners). | `technical_release_gate`, `technical_production_smoke`, `technical_build`, `technical_unit_tests`, `technical_e2e`, `technical_secret_scan` | Ingested ONLY from CI artifact records or ingestion payloads; cannot be dynamically fabricated by Node runtime |
| `PERSISTED_EVIDENCE` | State verified against version-controlled repository assets and migration logs. | `technical_database_reproducibility` (e.g. `20260918004527_remote_schema.sql`) | Ingested or verified via migration history |
| `MANUAL_EVIDENCE` | Data verified by human audits, legal reviews, or external merchant credentials. | Investor terms, privacy policy compliance, vendor SLA agreements | Recorded with `provided_by` and audit reference |
| `NOT_MEASURED` | Required dimensions that lack current, validated evidence. | Multi-user load tests (100-500+ CCU), provider billing statements | Set to `NOT_MEASURED` or `NOT_MEASURED_AT_SCALE` |

## 3. Removal of Stale Hardcoded Test Counts

All static, mutable test counts (such as `66/66`, `76/76`, `78/78`, `83/83`, `20/20`) have been removed from runtime code. Test execution numbers belong to CI pipelines and test execution reports. Runtime assessments now evaluate deterministic semantic status (`PASS`, `FAIL`, `STALE`, `NOT_MEASURED`) backed by `validated_commit_sha`.

---

## 4. Commit Freshness & Identity (`validated_commit_sha`)

Technical readiness is strictly tied to the commit running in production:
1. `currentCommitSha` is resolved from:
   - Request query/body override (`req.query.commit_sha`, `req.body.commit_sha`)
   - `process.env.RAILWAY_GIT_COMMIT_SHA`
   - `process.env.GIT_COMMIT_SHA`
   - `process.env.COMMIT_SHA`
2. Each CI dimension records `validated_commit_sha`.
3. If `validated_commit_sha !== currentCommitSha`, the dimension is marked `STALE` and fails readiness.
4. If `currentCommitSha` cannot be resolved or evidence is absent, the dimension is marked `NOT_MEASURED`.

Readiness evaluation rules exposed in summary:
- `technicalEvidenceComplete`: All required dimensions have status !== `'NOT_MEASURED'`.

- `technicalRequiredPass`: `technicalEvidenceComplete && technicalEvidenceCurrent && allDimensionsPass && openSecurityBlockers === 0`.

## 6. Runtime Health vs. Scale Capacity Separation

- `railway_runtime_capacity`: Classified as `semantic_dimension: 'runtime_health'`, `is_scale_capacity: false`. Telemetry reports single-container RSS memory; it does NOT prove multi-user scale concurrency.
- `supabase_database_capacity`: Classified as `semantic_dimension: 'database_runtime_health'`, `is_scale_capacity: false`. Single-query connectivity does NOT prove connection pool resilience under peak load.
- `synthetic_vs_load_testing`: Classified as `semantic_dimension: 'capacity.load_test'`, `is_scale_capacity: true`.
- `isCapacityLoadMeasured`: Evaluates `true` ONLY if `meta.is_scale_capacity === true && meta.load_test_evidence && meta.load_test_evidence.concurrent_users > 0`. Since production load testing has not been run, this dimension remains `NOT_MEASURED_AT_SCALE`, and `isCapacityLoadMeasured = false`.
