## Executive Findings

- PL20 tables exist in production and contain rows, but most PL20 rows are seeded or generated by admin smoke/API endpoints, not by independently measured commercial, billing, or high-load telemetry.
- Real commercial aggregates are available from existing production tables such as `orders`, `order_items`, `stripe_events`, `email_events`, `abandoned_carts`, `conversion_events`, `order_timeline`, `inventory_movements`, `support_messages`, and `reviews`.
- Current production order volume is low. Paid-like commercial evidence exists, but it is insufficient for broad investor-scale claims without clear metric definitions and more operating history.
- Operating cost evidence is not measured. `operating_cost_summaries` contains one row with all provider estimates set to `0.00`; this should be treated as `NOT_MEASURED`.
- Capacity evidence is not measured at scale. Existing PL20 capacity records and source comments explicitly note that real 100-500+ concurrent-user load testing was not performed.
- Investor readiness evidence is partial: technical QA/security evidence is strong, but commercial traction, real operating costs, and scale capacity are incomplete.
- Schema extension is recommended for durable PL20 metric snapshots and provenance. Existing `metadata` / `evidence` JSONB fields can hold provisional provenance, but a stable metric contract needs source, period, freshness, calculation method, and measured/not-measured state.

## Commercial Data Sources

Use these sources for PL20 calculations:

- `orders`: order count, paid-like count, gross revenue, refunded amount, net revenue, AOV, customer aggregate counts, fulfillment/financial status.
- `order_items`: units, item mix, product-level aggregation when joined through orders.
- `stripe_events`: checkout completion/expiration evidence and payment lifecycle event counts.
- `email_events`: transactional/recovery/admin email delivery evidence.
- `abandoned_carts`: cart abandonment and possible recovery evidence if recovery fields are present and contracted.
- `conversion_events`: funnel events such as add-to-cart and experiment assignment.
- `order_timeline`: fulfillment/status operational history.
- `inventory_movements`: stock movement evidence tied to sales.
- `support_messages`: support load and response readiness inputs.
- `reviews`: customer review/social proof evidence; currently empty.
- `audit_logs`: admin action and operational process evidence.

Avoid using all-order revenue as commercial revenue without status filtering. Current all-order gross total is inflated by canceled orders.

## Minimum Evidence Threshold

For honest PL20 readiness:

1. Technical readiness can be considered evidence-backed only if release gate, production smoke, security baseline, and deployment commit evidence are current.
2. Commercial readiness must use paid-like order/revenue definitions and must not include canceled orders as revenue.
3. Cost readiness must use real provider billing, plan cost, or explicit user-approved estimates. Zero-filled cost rows are not acceptable proof.
4. Capacity readiness must use real concurrent-user testing or be marked `NOT_MEASURED`.
5. Investor readiness must surface missing cost/capacity/commercial-history evidence instead of compressing it into static green scores.
6. Every score must be traceable to source rows, external evidence, or a declared `NOT_MEASURED` state.

## Schema Extension Assessment

Existing PL20 schema is sufficient for a provisional evidence handoff because `metadata` and `evidence` JSONB fields exist.

However, schema extension is recommended if PL20 is expected to become a repeatable production/investor reporting system. The current schema does not enforce source periods, freshness, measured state, calculation version, or provider-level provenance. Without those fields, score rows can remain static while appearing authoritative.

Recommended direction for ChatGPT Web review:

- add or define a durable metric snapshot structure;
- require explicit `measured_state`;
- preserve raw aggregate values separately from derived scores;
- include source table/provider and calculation window;
- mark cost and capacity metrics as `NOT_MEASURED` until real provider/load evidence exists.
